# Local API v1

Base path `/api`. Direct TCP/LAN endpoints require `Authorization: Bearer ACCESS_KEY`. The private Tailscale Serve Unix listener authenticates requests through its trusted transport; implicit POST requests must carry the configured HTTPS `Origin`. No CORS is enabled. Credentials for Tucor are never returned. `GET /healthz` is a separate unauthenticated process-liveness check, not proof of a controller connection.

`GET /api/auth` is public and reports `{authenticated, mode}` for the current request. Mode is `tailscale` on the trusted private listener and `key` on TCP. The UI uses this endpoint to skip its access-key form only for implicit Tailscale authentication; the server independently authorizes every API request. See `deploy/tailscale-auth.md`.

`GET /api/state` returns cached controller status, availability, zone inventory/run ownership, policy, the last weather decision, the latest 50 activity records, and up to 50 command operations (pending first). The last observation is persisted for quick inventory display after restart; its timestamp is never renewed just by reading it. `POST /api/refresh` with `{}` requests a fresh controller observation. Concurrent refreshes are coalesced and pending refreshes yield to commands. Live mode never refreshes in the background; while a session is open, pushed controller updates replace the cached observation without new requests. UI status polling reads only the cache every 1.5 seconds while visible.

`POST /api/prepare` with `{}` immediately returns 202 and warms a controller session in the background. The web app calls it on opening/unlocking, after a pause in interaction, and once a minute while someone keeps using the app, never on each status poll. Interactive sessions are retained for 90 seconds after use, with a ten-minute maximum lifetime. Weather writes never extend that idle timeout; their sessions are released after a one-second handoff window. A command arriving during refresh reuses its session. Warm sessions use receipt timestamps for controller mode, rain hold, and stations, requesting new observations when these are over three seconds old. A disconnected/failed session is discarded; writes are never automatically replayed.

Every mutation below requires `Content-Type: application/json`, a unique `Idempotency-Key` header (8–100 alphanumeric/hyphen/underscore characters), and an ISO `deadline` in the body no more than 120 seconds in the future. Clients use 60 seconds. The remaining properties are:

| POST path | Properties | Meaning |
| --- | --- | --- |
| `/api/zones/:id/start` | `minutes`: integer 1–240 | Single bounded run; rejects overlap, rain delay, non-Automatic mode |
| `/api/zones/:id/stop` | none | Stop recorded owned handle for this zone |
| `/api/zones/:id/next` | `minutes`: integer 1–240 | Confirm stop of owned runs, then check safety and start the target; one server-owned operation |
| `/api/stop` | none | Stop all recorded owned runs |
| `/api/zones/:id/preferences` | optional `name`, `notes`, `order`, `favorite`, `issues` (up to 20 `{issue, at}`; `issue` ≤ 40 characters, `at` ISO time) | Local metadata; does not change Tucor configuration |
| `/api/rain` | `hours`: integer 0–999 | Explicit manual hold replacement; 0 clears |
| `/api/policy` | any subset of policy fields below | Persist settings |
| `/api/weather` | `observedAt`, optional `intensityMmH`, `accumulationMm`, `forecastMm`, `forecastProbability` | Submit normalized weather observation |

### Watering plan

Intentions are local planning data. They never reach Tucor and do not change controller schedules. Intent and night-setting writes are idempotent replacements answered immediately, outside the command queue; they need JSON and the usual authentication but no `Idempotency-Key` (a `deadline` is ignored).

| POST path | Properties | Meaning |
| --- | --- | --- |
| `/api/zones/:id/intent` | any of `seconds` (100% baseline, integer 1–14400 or null), `seasonalPercent` (integer 50–200, default 100), `cadence` (`{every: 1–30}` days, `{perWeek: 1–6}`, or null), `enabled` (boolean), `waterDuringRain` (boolean, default false), `firstDue` (`YYYY-MM-DD` or null) | Merge into the zone's intention; returns `{ok, intent}` |
| `/api/plan/seasonal` | `seasonalPercent` (integer 50–200) | Atomically replace the percentage for every known zone and saved intention, including disabled zones; returns `{ok, plan}` |
| `/api/plan` | any of `earliestStart` (minutes after the evening's midnight, 1080–1560), `finishBeforeSunrise` (0–120), `hardDeadline` (minutes after the morning's midnight, 240–720), `lanes` (1–2) | Night settings (`lanes` is a maximum; one zone is preferred, with minimum overlap when a second is needed before the preferred finish); returns `{ok, settings}` |

`GET /api/state` includes `plan: {settings, intents, seasonalZoneIds}` (intents keyed by zone id) and `location` (`{latitude, longitude}` of the Tempest, recorded from WeatherFlow, or null). Complete intentions receive a persisted initial date automatically, balanced around existing intentions. Existing dates survive restarts, duration edits, and rain-preference edits. Changing cadence preserves the next projected watering date and starts the new cadence there. `firstDue` remains a compatibility field; the UI does not ask owners to select dates. `waterDuringRain` exempts a zone only in the advisory projection; it does not bypass controller rain shutdown or manual-command checks. The app projects nights from these with `lib/planner.mjs`, served to the browser as `/planner.js`.

`POST /api/plan/rebalance-preview` with `{}` returns a read-only proposal: `{token, changes, beforePeakSeconds, afterPeakSeconds}`. Each change contains a zone id, old/new next watering date (`before`, `after`), signed `days` shift, and proposed internal `firstDue`. Peak values are total zone runtime on the busiest regular night across twelve weeks, before rain holds. The greedy proposal moves only enabled, complete zones, requires a lower peak at each step, and may return no changes.

`POST /api/plan/program-preview` with `{}` compiles the saved intentions into a dry-weather repeating program candidate. Optional `{enabledOverrides: {"15": true, "16": true}}` compares seasonal availability without saving it. Only known zone ids and boolean overrides are accepted. The usual authentication/JSON rules apply; no command idempotency key is needed. This endpoint does not contact Tucor or write local preferences.

The response includes `dryRun: true`, `status` (`candidate` or `blocked`), `issues`, `summary`, `horizon`, `programs`, and fourteen `nights`. Each program contains a proposed `slot`, sequential `steps` (`zone`, `name`, `seconds`), `budgetPercent: 100`, `waterDuringRain` as a policy requirement only, `startMinute` relative to the evening midnight, `clockMinute`, and `startDayOffset`. `eveningMask` indexes the nights starting at `calendarAnchor`; `calendarMask` rotates that mask onto actual program-start dates after midnight. Both are an intermediate representation, **not verified vendor calendar encoding or a sync payload**. `summary.parallelSeconds` is elapsed time with two active zones across all fourteen nights. `minimumOverlapProven` compares it with a workload lower bound for the chosen common window; otherwise the candidate may be improvable.

The compiler targets the earliest preferred sunrise finish across the fourteen mornings, rounded down to a minute. It tries sequential programs first, then two concurrent programs if allowed, then the hard deadline. Search is bounded and deterministic. It reports unsupported cadences, transient anchors, unrepresentable LTD seconds, more than ten calendar/rain groups, and unsuccessful packing explicitly. Oversized identical-calendar groups can be split into whole-zone programs when slots permit. This version does not combine different calendars; a blocked result is not proof no controller arrangement exists. Missing location uses the preview's fallback sunrise and sets `horizon.sunriseKnown: false`. Future sunrise/DST drift, rain recovery, step capacity, program sync and controller readback remain outside this dry run. The server's local timezone must match the controller.

`POST /api/plan/edit-preview` accepts `{change}` (or `{}` for the saved-plan check). `change` can contain `intents: {zoneId: intentPatch}`, `settings: settingsPatch`, `seasonalPercent`, `seasonalZoneIds: [zoneId, ...]`, or `rebalanceToken` from the rebalance preview. Changes can be combined. Validation and cadence/date normalization are identical to ordinary plan writes, but no preferences or controller state are changed. Empty unnamed slots are excluded from compilation even if global seasonal adjustment has created placeholder intentions for them.

It returns `{token, plan, assessment, seasonalZones, alternatives}`. Assessment statuses are `fits`, `consequence`, or `needs-adjustment`; scenarios cover the draft's enabled states and the selected seasonal zones forced off/on. Consequences include added simultaneous-watering seconds, affected nights, later finishes, and use of time past the preferred target, compared with the saved plan under the same scenario. Failures distinguish calendar patterns, overnight capacity, unsupported cadence/precision, incomplete intentions, transition dates, and a bounded search that found no candidate. The ten-program detail is diagnostic, not a generic “full” warning. Seasonal checks use the current fourteen-night sunrise horizon, not a prediction of next summer or rain recovery.

Alternatives are bounded, deterministic searches verified against every scenario. Date alternatives shift only edited zones, preserving the requested cadence and amount and disclosing the next date and first shorter/longer gap. Timing alternatives change the earliest start, hard deadline, or maximum concurrent zones. Frequency alternatives explicitly disclose the changed weekly frequency and runtime. No alternative is a generic untested suggestion. An empty list does not prove the user's goal impossible.

`POST /api/plan/edit-apply` accepts `{change, token, alternativeId?, saveUnresolved?}`. It rechecks the saved plan, zone inventory/names, location, and local night, and recomputes the chosen verified alternative. A stale token returns 409 without saving. A still-unresolved draft requires `saveUnresolved: true`; choosing an alternative applies exactly its disclosed adjustments. Intentions, settings, and the seasonal selection save in one transaction. Returns `{ok, plan, assessment}`. Both endpoints have the normal authenticated JSON/origin requirements and never contact Tucor. The older plan-write endpoints remain available for compatibility; the web editor uses this reviewed path for zone edits, night settings, global seasonal changes, and rebalancing.

Seasonal comparison ids are saved separately from zone enablement. The initial default includes named vineyard zones and currently paused zones; the user can change the selection in the fit panel. Selecting a comparison zone never enables its actual watering. The web editor keeps unsaved changes in tab-scoped session storage and restores them for review, without automatically applying them after reload.

Existing durations are the 100% baseline; missing `seasonalPercent` reads as 100. Projected durations are `round(seconds * seasonalPercent / 100)`, with a one-second minimum for a configured run. Night capacity, weekly totals, staggering and rebalance loads use these adjusted durations. Percentages never compound or overwrite baseline seconds, change cadence, enable disabled zones, or move existing anchors. Setting all zones overwrites individual percentages; subsequent zone edits can override them. Disabling a zone remains the way to omit its watering. Preview durations above four hours are allowed and may be deferred by night capacity; manual controller runs retain their four-hour limit. Seasonal edits are local and have the same authentication and JSON requirements as other plan edits, with no command idempotency key required.

`POST /api/plan/rebalance` with `{token}` applies the reviewed proposal atomically to local dates. A token is bound to the entire saved plan and current night; intervening edits or a new night return 409 and require a new review. Duration, cadence, rain flags, and disabled zones are unchanged. These endpoints use the same authentication and JSON requirements as other plan endpoints, without command idempotency keys. They never contact Tucor. Disabling or enabling a zone does not implicitly rebalance anything, and editing a disabled zone's cadence does not enable it.

Policy fields: `mode` (`off`, `observe`, `automatic`), `intensityMmH` (0.01–100), `accumulationMm` and `forecastMm` (0.1–500), `forecastProbability` (1–100), `holdHours` (integer 1–72).

By default mutations wait for confirmation and return their existing result. With `Prefer: respond-async`, the server commits the command to SQLite and immediately returns **202** with `{operation}` and a `Location: /api/commands/:id` header. Acceptance means the bridge will attempt the operation within its deadline; it does not mean the controller has acted. Execution continues independently of the HTTP connection or phone. Payload/safety failures appear in the operation's final result. `GET /api/commands/:id` (authenticated) returns `{operation}`: `id`, `kind`, `body`, `acceptedAt`, `deadline`, `phase`, `state` (`pending`, `succeeded`, `failed`), and `result`. The phase distinguishes queued, connecting, sending, and confirming. Terminal duplicate async requests return 200 with the recorded operation.

Successful duplicate keys with identical payloads return the recorded result without re-executing. Concurrent duplicates join the same operation. Reusing a key for different content fails. Failed requests cannot be replayed; commands pending at server restart become failed with an explicit unknown-outcome message and are **not resumed**. Accepted work survives closing the phone, not a server crash. A failed write can have an unknown physical outcome; refresh and inspect before deliberately making a new request. Keys and operation records are retained indefinitely. The UI remembers its last request ID and checks status after reopening or losing an acknowledgement; it never automatically sends it again.

`available` means the last successful controller observation is under three minutes old and no later connection error is recorded. `connection` reports whether a Tucor session is `open`, whether a refresh is `checking`, `retryAt` during backoff, `lastError`, `lastSuccessAt`, `sessionsLastHour` and `loginsToday` against `limits` (`sessionsPerHour`, `loginsPerDay`), and the latest connection `history` with any Tucor status `codes`. New sessions beyond the limits are refused with an explanatory error before anything is sent to Tucor; during backoff only explicit commands may connect. `weatherSource` reports whether a Tempest station is configured and its `station` (`id`, `name`). `weatherReading` holds the latest weather `sample` and its time, or the latest read `error`. `controlEnabled` is a separate server switch. `limits` reports `minMinutes`, `maxMinutes`, `concurrentZones` and the per-zone `issues` cap so clients need not hardcode them. Zone `startedAt`, `minutes` and `endsAt` describe a confirmed owned run (null otherwise); `endsAt` is an estimate; the controller remains responsible for the timer. The UI keeps showing a run until a fresh observation confirms it stopped.

Typical errors: 400 invalid/expired request; 401 bad API key; 403 live controls disabled; 404 unknown route/zone; 409 conflicting/unsafe state or reused command; 503 connection failure or unconfirmed outcome. No automatic write retries. A successful response confirms an observed protocol state, not physical valve movement.
